## Env vars / secrets

Referenced: server-only `GOOGLE_CLOUD_API_KEY`; optional `GEMINI_MODEL` override (default `gemini-3.1-flash-lite`); server-only `PRESSROOM_API_KEY` for the blog; and Turnstile site + secret keys. The hardened deployment contract requires distinct Generative Language API-restricted Gemini keys for the main web service and renderer, stored in `mathsolver-web-gemini-api-key` and `mathsolver-gemini-api-key`; the Turnstile server secret lives in `mathsolver-turnstile-secret`. Cloud Run deployments resolve the newest enabled version to an explicit numeric version before creating a revision, so rotations are pinned and rollback-safe rather than following `latest`. Legacy Azure chat values (`AZURE_OPENAI_*`) may remain in owner-side configuration and are unused. Narration and LLM calls have separate server-only `AZURE_TTS_*` and `AZURE_LLM_*` settings, so neither can reuse old chat credentials.

`LLM_PROVIDER=azure|gemini` selects every text/vision workload on web and mobile (solving, practice/questions/steps, OCR, Check My Work, completed-solution verification). The private video planner/reviewer has its own `VIDEO_LLM_PROVIDER` override (currently `gemini`); if absent, it inherits `LLM_PROVIDER` for backward compatibility. The code defaults to Gemini for compatibility; ignored root `.env` and the web deployment select Azure; lesson planning independently selects Gemini. Azure uses `AZURE_LLM_ENDPOINT` (the full `/openai/v1/responses` URL), `AZURE_LLM_API_KEY`, and `AZURE_LLM_DEPLOYMENT=gpt-4.1-nano`. Requests are stateless (`store: false`). GPT-4.1 nano uses the task temperature and visible-answer token budget without a reasoning parameter. Switching `AZURE_LLM_DEPLOYMENT` back to a `gpt-5` family deployment preserves low reasoning, omits temperature, and reserves 4,000 additional reasoning tokens. Deployment names should match the model family so this parameter selection is accurate. JSON mode includes an explicit JSON instruction in the input messages because Azure does not count the separate instructions field for that requirement. Solver SSE forwards only answer deltas, handles split UTF-8/events and cancellation, and rejects failed/incomplete/truncated streams. OCR preserves PDF data-URL input and the accepted image types, converting BMP/TIFF locally under a 40-megapixel bound, with a 60-second inference timeout. Gemini model/reviewer overrides remain available after rollback.

Root and renderer deploy scripts load ignored `.env`, respect explicit LLM overrides, and mount pinned versions of `WEB_AZURE_LLM_SECRET` (`mathsolver-web-azure-llm-api-key`) and `VIDEO_AZURE_LLM_SECRET` (`mathsolver-video-azure-llm-api-key`) respectively. `infra/video/setup.sh` creates these containers and grants each service access only to its own LLM secret. Add enabled secret versions before deploying; use `*_SECRET_VERSION` to pin an older enabled version. The Azure key is never a Cloud Run plain environment value or a build argument. Switch `LLM_PROVIDER=gemini` and redeploy both services to return all text/vision calls to Gemini; `VIDEO_TTS_PROVIDER` is independent. Pressroom's math authoring contract is explicit LaTeX: `\\(...\\)` for inline expressions and `\\[...\\]` for display expressions; dollar delimiters remain unsupported so financial prose cannot be misclassified. `pressroom-math.ts` uses `parse5` to transform text nodes only, skips code/pre/script/style/textarea/template/SVG/MathML and existing KaTeX, keeps invalid expressions as their original text, and renders with KaTeX `htmlAndMathml`, `trust: false`, and throwing syntax validation. Long display math has bounded horizontal overflow. The transformation runs after the five-minute cached article fetch, so a published Pressroom edit can take up to five minutes to appear.

## Persistence

Persistence is local-first. Signed-out data uses browser `localStorage` key `mathsolver_chats`. Signed-in account caches use `mathsolver_chats_user_{uid}`. Email/Password users can keep solving locally while verification is pending, but neither the client nor the checked-in rules permit cloud notebook access until `email_verified` is true. Google users arrive verified. A verified sign-in merges guest, account-cache, and Firestore chat versions by chat ID/latest `updatedAt`, imports the guest notebook, then debounces writes until streaming finishes. The browser notebook uses the Firestore Lite client because it performs only one-shot reads and batched writes; this avoids opening WebChannel listen streams and their noisy cancellation `AbortError`s during development navigation/HMR. Firestore documents live at `/users/{uid}/chats/{chatId}` and checked-in rules restrict all access to the matching verified UID. Deletes also write `/users/{uid}/chatDeletions/{chatId}` tombstones, preventing an older device cache from resurrecting a removed chat.

Chat text, OCR text, generated tests, generated explanations, per-question mistake-review schedules, and up to 20 recent completion attempts per test sync. Review state is nested on the existing question (`dueAt`, interval, review count, lapses, last review), so there is no duplicated question text or separate Firestore collection. Original uploaded image data URLs remain browser-local: cloud serialization retains their OCR text but removes the binary data to stay below Firestore's 1 MiB document limit. Chats are capped at 200 messages by rules; a future long-notebook design should move messages into subcollections before raising that limit.

Daily goal/streak state is a smaller device-local layer managed by `LearningProgressContext`, not Firestore. Guests use `mathsolver_learning_progress_v1`; signed-in browsers use `mathsolver_learning_progress_user_{uid}` and merge/remove guest progress at sign-in. Only boolean daily activity categories are retained (maximum 90 dates), with no problem content or identity data. Local calendar dates define day boundaries. This account-scoped cache does not yet provide cross-device streak sync.

The mobile notebook mirrors the verified-owner chat contract through Firestore REST and merges local guest history after verification. It persists solution metadata, quizzes, and spaced-review state locally first; photo bytes remain device-local. Account-owned notebook and offline-video records are keyed and validated against the active UID. Dirty uploads retry, delete tombstones block stale resurrection, and the sync coordinator rechecks the current local record after each cloud save so a delete or newer edit that races an older upload converges correctly. FCM auto-init is disabled until the learner explicitly requests video-ready notifications for that account. Registrations live at server-only `/users/{uid}/devices/{tokenHash}` plus `/mobileDevices/{tokenHash}` ownership records. Registering the same token for a different verified account transactionally removes previous ownership; sign-out/account deletion removes server and local ownership before clearing the session when online. Firestore rules explicitly deny all direct client access to both paths.

Visual lesson jobs live at `/users/{uid}/videoJobs/{jobId}` and the daily free allowance at `/users/{uid}/entitlements/video`. Both collections are explicitly server-only in Firestore rules. Web creation requires a fresh server-validated Turnstile token with the expected `mathsolver_request` action and production hostname; missing configuration or a Siteverify outage fails closed. Mobile creation follows a separate handler that requires Firebase App Check instead of Turnstile. Both paths then require a fresh verified-email Firebase ID token. Every verified account receives 10 generations per UTC day; the entitlement stores a `YYYY-MM-DD` period key, and API reads normalize an older or missing bucket to zero usage for the current day. Each charged job records its quota period so a failure after UTC midnight cannot decrement the next day's allowance. Job IDs are deterministic hashes of the UID and client request key, so reopening one answer does not consume another lesson. Rendering belongs to Cloud Tasks/Cloud Run, not the phone: screen-off or backgrounding suspends only mobile polling, and foreground resume reauthorizes/polls the same job without creating another request or spending quota again. The originating assistant message syncs only `{id, updatedAt}` for its attached job; the inline player reauthorizes through the job API and never stores signed URLs, object keys, or media bytes in the notebook. The planner accepts a damaged raw input only when the completed solution explicitly states one precise, correct interpretation, which the opening must disclose; it still rejects silent guesses and multiple plausible readings. A structurally invalid generated plan receives one feedback-guided regeneration, a mathematically rejected review receives the same bounded revision, and an unsupported job may be externally restarted once. Exhausted schema generation reports `planning_failed` rather than the misleading `render_failed`. Every supported plan has a required, unsafe-command-filtered `finalAnswerLatex`; review checks that it is complete and that final verification says the result aloud. Manim scenes render in isolated media directories; an `ENOENT` during partial-movie assembly receives one bounded fresh-directory retry, and the final scene ends on a deterministic 3.5-second answer card. FFmpeg then concatenates the normalized scene streams into one `full-lesson.mp4`; the manifest contains one clip, one continuous caption track, one poster, no mid-video interactions, and a transfer check remapped after `full-lesson`. Every unsuccessful same-day attempt refunds its reservation. Generation- and lease-scoped private object prefixes prevent retries or stale workers from overwriting a newer attempt; a lease cannot be stolen until it is ten minutes stale, and retry exhaustion is capped. Permanent deleted-user tombstones block late notebook, video, device, signed-URL, and notification writes/reads after account deletion. Only object keys—not video bytes or durable public URLs—enter Firestore. Signed URLs last 45 minutes and user deletion is available. Authenticated `GET /api/video/jobs` queries the latest 24 jobs within that user's subcollection and supplies short-lived poster metadata to `/video-library`; it never exposes a public/community gallery. Generation-specific scheduled Cloud Tasks are the authoritative 14-day metadata/media cleanup, with legacy-task compatibility and GCS lifecycle as the storage backstop. Managed Firestore TTL is only supplemental and is currently unavailable while billing is disabled on the Firebase project. Failed and unsupported generations transactionally refund the applicable daily allowance.
