## Stack

- **Framework:** Next.js 16.2.12 (App Router), React 19.2, React Compiler (`babel-plugin-react-compiler`), TypeScript.
- **Styling:** Tailwind CSS v4, `@tailwindcss/typography`, `framer-motion`, `lucide-react`, `next-themes`.
- **Math:** KaTeX + `react-markdown` + `remark-math` + `rehype-katex`; `mathlive` for input; `react-resizable-panels` for split view.
- **Build/host:** Docker (`Dockerfile`, `cloudbuild.yaml`, Next `output: "standalone"`) → Artifact Registry → **Google Cloud Run** (`deploy.sh`; project `axial-willow-428621-n4`, `us-central1`, 4Gi/2CPU, max 20 instances). `.gcloudignore` keeps local caches and the separately released `mobile_app/` tree out of web build uploads.
- **Visual lessons:** Next.js job API + Cloud Tasks → private Python/FastAPI Cloud Run worker with Pydantic, Gemini, Manim, LaTeX, and FFmpeg → private regional Google Cloud Storage.
- **Mobile:** isolated Flutter 3.44/Dart 3.12 app in `mobile_app/`; light-first Material 3, crop-aware camera/gallery capture, streamed HTTP, native LaTeX, secure session storage, Firestore REST sync, Firebase App Check/Analytics/Messaging, video playback/offline caching, and native sharing. Android min SDK 24 and iOS min 15; both use `io.mathsolver.app`.

## Env vars / secrets

Referenced: server-only `GOOGLE_CLOUD_API_KEY`; optional `GEMINI_MODEL` override (default `gemini-3.1-flash-lite`); server-only `PRESSROOM_API_KEY` for the blog; and Turnstile site + secret keys. The hardened deployment contract requires distinct Generative Language API-restricted Gemini keys for the main web service and renderer, stored in `mathsolver-web-gemini-api-key` and `mathsolver-gemini-api-key`; the Turnstile server secret lives in `mathsolver-turnstile-secret`. Cloud Run deployments resolve the newest enabled version to an explicit numeric version before creating a revision, so rotations are pinned and rollback-safe rather than following `latest`. Legacy Azure values may remain in owner-side deployment configuration but are no longer read by the application.

Pressroom's math authoring contract is explicit LaTeX: `\\(...\\)` for inline expressions and `\\[...\\]` for display expressions; dollar delimiters remain unsupported so financial prose cannot be misclassified. `pressroom-math.ts` uses `parse5` to transform text nodes only, skips code/pre/script/style/textarea/template/SVG/MathML and existing KaTeX, keeps invalid expressions as their original text, and renders with KaTeX `htmlAndMathml`, `trust: false`, and throwing syntax validation. Long display math has bounded horizontal overflow. The transformation runs after the five-minute cached article fetch, so a published Pressroom edit can take up to five minutes to appear.

Contact delivery uses server-only `TELEGRAM_BOT_TOKEN` plus `TELEGRAM_CHAT_ID`. Local development may load both from an ignored env file. For production, store the rotated token in the Secret Manager resource named by `TELEGRAM_BOT_SECRET` (default `mathsolver-telegram-bot-token`), put only the numeric chat ID in ignored deployment configuration, and let `deploy.sh` pin `TELEGRAM_BOT_SECRET_VERSION` or the newest enabled version. The destination account must open the bot and press **Start** before Telegram permits the bot to send it a private message; otherwise Telegram returns `400 Bad Request: chat not found`, which the contact API exposes as a generic 502 delivery failure. `CONTACT_TURNSTILE_HOSTNAMES` defaults to the production root and `www` hosts. If no chat ID is configured, deployment leaves the optional contact bindings unchanged; the route fails safely with 503 when either runtime value is absent.

Visual-lesson runtime variables are documented in `.env.example`: `FIREBASE_ADMIN_PROJECT_ID`, `VIDEO_STORAGE_BUCKET`, `VIDEO_QUEUE_MODE`, `VIDEO_QUEUE_PROJECT`, `VIDEO_QUEUE_LOCATION`, `VIDEO_QUEUE_NAME`, `VIDEO_RENDERER_URL`, and `VIDEO_TASK_SERVICE_ACCOUNT`. The launch allowance is fixed in code at exactly 10 videos per verified account per UTC day, so production configuration cannot silently raise it. Local direct dispatch additionally needs `VIDEO_DIRECT_RENDER_SECRET`. Production uses Application Default Credentials and Cloud Run IAM; never add a service-account JSON file. The existing ignored local Firebase Admin credential can run the real Cloud Tasks preview through narrow cross-project IAM: queue enqueuer, task-service-account user, and read-only access to the private video bucket. It deliberately cannot write or delete video objects. The renderer receives its dedicated Gemini key from Secret Manager as `GOOGLE_CLOUD_API_KEY`; Gemini requests send that key in the `x-goog-api-key` header, never in a URL.

Optional Firebase Web app values: `NEXT_PUBLIC_FIREBASE_API_KEY`, `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`, `NEXT_PUBLIC_FIREBASE_PROJECT_ID`, `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET`, `NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID`, `NEXT_PUBLIC_FIREBASE_APP_ID`. These public identifiers and `NEXT_PUBLIC_TURNSTILE_SITE_KEY` are listed in `.env.example`; they are not service-account credentials. Next embeds them at build time, so Docker must receive them as build arguments rather than only setting Cloud Run runtime env vars. `deploy.sh` loads the public values from ignored local configuration, supplies them to `cloudbuild.yaml`, mounts pinned web-Gemini and Turnstile Secret Manager versions, and deploys the tagged image while preserving unrelated runtime variables such as `PRESSROOM_API_KEY`.

Never print, echo, or commit API keys, Turnstile secrets, service-account credentials, or signed playback URLs. When rotating a production secret, add and validate a new enabled version, deploy the explicitly pinned revision, and disable the old version only after the new revision passes smoke checks.

The Flutter client defaults to `https://math-solver.io` and accepts `MATHSOLVER_API_BASE_URL` through `--dart-define`. Platform-specific `MATHSOLVER_FIREBASE_IOS_API_KEY` and `MATHSOLVER_FIREBASE_ANDROID_API_KEY` values initialize Firebase; `MATHSOLVER_FIREBASE_API_KEY` remains a compatibility fallback. `mobile_app/tool/configure_firebase.mjs` uses the ignored local Admin credential only to read registered native SDK/provider configs, then writes mode-`0600`, Git-ignored `firebase.local.json` and `ios/Flutter/FirebaseLocal.xcconfig` files containing public API/OAuth client values and Google/Apple readiness flags. `run_with_firebase.sh` supplies the JSON to Flutter, while the Xcode include supplies the reversed Google callback scheme for direct workspace runs. Native Firebase Authentication persists and refreshes verified Email/Password, Google, and Apple sessions; the Apple private key stays only in Apple/Firebase owner configuration. The compatible package set pins `firebase_core` 4.12.1, `firebase_auth` 6.5.6, and `firebase_core_platform_interface` 8.0.0 to avoid the incompatible iOS Pigeon schema in interface 8.1.0. Native App Check uses App Attest with DeviceCheck fallback on iOS and Play Integrity on Android; debug builds use registered debug tokens. `/api/mobile/v1/*` validates the `X-Firebase-AppCheck` header through Admin SDK and rejects invalid presented tokens; attested non-video calls bypass the web fallback limiter, video job creation always requires a valid App Check token, and the broader gateway can be rolled out with `MOBILE_APP_CHECK_ENFORCED=true` after metrics establish legitimate traffic. Account-owned routes also require fresh verified-email Firebase ID tokens. Never track API keys, OAuth private keys, debug tokens, APNs keys, keystores, signing certificates, or store credentials.

`GET /api/mobile/v1/app-config` compares the installed semantic version with platform-specific latest/minimum environment values. A newer ordinary release returns a dismissible recommendation that is remembered per target version. A minimum version can block only when the reason is exactly `security` or `compatibility` and a valid HTTPS store URL is configured; invalid reasons (including ads/marketing) degrade to an optional recommendation. A required policy is cached on-device for offline safety and is cleared after a successful server response removes the gate.

`DELETE /api/mobile/v1/account` requires App Check, a verified Firebase session, and an authentication time within 10 minutes. The app reauthenticates immediately with the account's actual Apple, Google, or Email/Password provider before calling it. Deletion removes private video objects, notification ownership, the full Firestore user subtree, and finally the Firebase Auth user; the client then removes locally saved learning data and offline lesson media.

## Persistence

Persistence is local-first. Signed-out data uses browser `localStorage` key `mathsolver_chats`. Signed-in account caches use `mathsolver_chats_user_{uid}`. Email/Password users can keep solving locally while verification is pending, but neither the client nor the checked-in rules permit cloud notebook access until `email_verified` is true. Google users arrive verified. A verified sign-in merges guest, account-cache, and Firestore chat versions by chat ID/latest `updatedAt`, imports the guest notebook, then debounces writes until streaming finishes. The browser notebook uses the Firestore Lite client because it performs only one-shot reads and batched writes; this avoids opening WebChannel listen streams and their noisy cancellation `AbortError`s during development navigation/HMR. Firestore documents live at `/users/{uid}/chats/{chatId}` and checked-in rules restrict all access to the matching verified UID. Deletes also write `/users/{uid}/chatDeletions/{chatId}` tombstones, preventing an older device cache from resurrecting a removed chat.

Chat text, OCR text, generated tests, generated explanations, per-question mistake-review schedules, and up to 20 recent completion attempts per test sync. Review state is nested on the existing question (`dueAt`, interval, review count, lapses, last review), so there is no duplicated question text or separate Firestore collection. Original uploaded image data URLs remain browser-local: cloud serialization retains their OCR text but removes the binary data to stay below Firestore's 1 MiB document limit. Chats are capped at 200 messages by rules; a future long-notebook design should move messages into subcollections before raising that limit.

Daily goal/streak state is a smaller device-local layer managed by `LearningProgressContext`, not Firestore. Guests use `mathsolver_learning_progress_v1`; signed-in browsers use `mathsolver_learning_progress_user_{uid}` and merge/remove guest progress at sign-in. Only boolean daily activity categories are retained (maximum 90 dates), with no problem content or identity data. Local calendar dates define day boundaries. This account-scoped cache does not yet provide cross-device streak sync.

The mobile notebook mirrors the verified-owner chat contract through Firestore REST and merges local guest history after verification. It persists solution metadata, quizzes, and spaced-review state locally first; photo bytes remain device-local. FCM auto-init is disabled until the learner requests video-ready notifications. Registrations live at server-only `/users/{uid}/devices/{tokenHash}` plus `/mobileDevices/{tokenHash}` ownership records. Registering the same token for a different verified account transactionally removes previous ownership; manual sign-out removes the server registration and local token before clearing the session when online. Firestore rules explicitly deny all direct client access to both paths.

Visual lesson jobs live at `/users/{uid}/videoJobs/{jobId}` and the daily free allowance at `/users/{uid}/entitlements/video`. Both collections are explicitly server-only in Firestore rules. Web creation requires a fresh server-validated Turnstile token with the expected `mathsolver_request` action and production hostname; missing configuration or a Siteverify outage fails closed. Mobile creation follows a separate handler that requires Firebase App Check instead of Turnstile. Both paths then require a fresh verified-email Firebase ID token. Every verified account receives 10 generations per UTC day; the entitlement stores a `YYYY-MM-DD` period key, and API reads normalize an older or missing bucket to zero usage for the current day. Each charged job records its quota period so a failure after UTC midnight cannot decrement the next day's allowance. Job IDs are deterministic hashes of the UID and client request key, so reopening one answer does not consume another lesson. The originating assistant message syncs only `{id, updatedAt}` for its attached job; the inline player reauthorizes through the job API and never stores signed URLs, object keys, or media bytes in the notebook. The planner accepts a damaged raw input only when the completed solution explicitly states one precise, correct interpretation, which the opening must disclose; it still rejects silent guesses and multiple plausible readings. A structurally invalid generated plan receives one feedback-guided regeneration, a mathematically rejected review receives the same bounded revision, and an unsupported job may be externally restarted once. Exhausted schema generation reports `planning_failed` rather than the misleading `render_failed`. Every supported plan has a required, unsafe-command-filtered `finalAnswerLatex`; review checks that it is complete and that final verification says the result aloud. Manim scenes render in isolated media directories; an `ENOENT` during partial-movie assembly receives one bounded fresh-directory retry, and the final scene ends on a deterministic 3.5-second answer card. FFmpeg then concatenates the normalized scene streams into one `full-lesson.mp4`; the manifest contains one clip, one continuous caption track, one poster, no mid-video interactions, and a transfer check remapped after `full-lesson`. Every unsuccessful same-day attempt refunds its reservation. Only object keys—not video bytes or durable public URLs—enter Firestore. Generated video, captions, poster, and manifest use the private `video-lessons/{uid}/{jobId}/` GCS prefix; signed URLs last 45 minutes and user deletion is available. Authenticated `GET /api/video/jobs` queries the latest 24 jobs within that user's subcollection and supplies short-lived poster metadata to `/video-library`; it never exposes a public/community gallery. A scheduled per-job Cloud Task is the authoritative 14-day metadata/media cleanup, with GCS lifecycle as the storage backstop. Managed Firestore TTL is only supplemental and is currently unavailable while billing is disabled on the Firebase project. Failed and unsupported generations transactionally refund the applicable daily allowance.

## Visual lesson operations

- `infra/video/setup.sh` idempotently enables APIs, creates the private regional bucket and service accounts, applies CORS/lifecycle/public-access prevention, creates the rate-limited Cloud Tasks queue, grants least-privilege cross-project IAM, creates separate renderer-Gemini, web-Gemini, and Turnstile Secret Manager containers, and attempts to enable Firestore TTL on `deleteAt`; when TTL is unavailable, it warns and retains scheduled Cloud Tasks cleanup as authoritative. Its bucket bindings use custom object-only roles: the renderer can create/replace/read/list/delete lesson objects, while the web service can only read/list/delete them and signs URLs through its existing self-signing permission. The setup removes their legacy bucket-wide `roles/storage.objectAdmin` bindings after the custom roles are in place.
- Add separate Generative Language API-restricted Gemini keys to the renderer and web secrets and add the Turnstile server secret without printing them. `services/video-renderer/deploy.sh` and root `deploy.sh` discover the newest enabled secret versions and pin their numeric version in the new Cloud Run revision; explicit `*_SECRET_VERSION` overrides support rollback. The renderer deploy keeps unauthenticated access disabled, grants only the task service account `run.invoker`, explicitly routes 100% traffic to the newly created revision even when Cloud Run previously pinned traffic to an older revision, and normally adds the required video runtime variables to the main `mathsolver` service. For renderer-only work, use `VIDEO_SKIP_BUILD=true` to reuse the current image and `VIDEO_UPDATE_WEB_SERVICE=false` to leave the main service untouched.
- Local Cloud Tasks preview must keep the non-secret `VIDEO_*` queue/renderer/bucket values plus `GOOGLE_CLOUD_PROJECT` in ignored `.env.development.local`; supplying them only inline to one `npm run dev` process makes video dispatch revert to unconfigured direct mode after the next restart. Restart the dev server after changing these values. The owner credential path and API keys remain ignored and must never be copied into tracked files.
- Renderer reliability defaults are two bounded planner/reviewer passes (`VIDEO_PLAN_ATTEMPTS=2`) and up to five transcription-gated TTS attempts per phrase (`VIDEO_TTS_ATTEMPTS=5`). Voice work is deliberately sequential (`VIDEO_TTS_WORKERS=1`) to reduce preview-model contention; narration uses short, fully spoken math phrases, and QA canonicalizes equivalent forms such as “negative twelve over thirty-five” and `-12/35` before applying the unchanged transcript-similarity gate.
- `infra/video/bucket-cors.json` is the durable private-media CORS policy. It allows the production hosts plus local ports 3000–3003 for both `localhost` and `127.0.0.1`, because Next selects the next free port during parallel local runs. Apply it with the setup script or `gcloud storage buckets update`; changing this bucket policy does not require a web deployment.
- Deploy the main Next.js image afterward with root `deploy.sh`, then publish `firestore.rules`. The production smoke script needs one fresh single-use `VIDEO_SMOKE_TURNSTILE_TOKEN` for job creation. Queue defaults are two dispatches/second, three concurrent renders, three attempts; worker defaults are 2 CPU, 4 GiB, concurrency 1, max three instances, 900-second timeout.
- Do not log the problem, solution, narration, signed URLs, Firebase UID, or object keys. HLS/R2/Mux remain later measured optimizations; the MVP serves small independent H.264/AAC MP4 clips directly from GCS.

## Analytics contract

`src/lib/analytics.ts` queues GA4 events even if `gtag.js` is still loading. The retention contract is intentionally narrow:

| Event | Parameters |
|---|---|
| `learning_return` | `days_away`: `1`, `2_7`, `8_30`, or `31_plus` |
| `learning_activity` | `activity`: `solve`, `practice`, or `review` |
| `daily_goal_action_clicked` | `action`: `solve`, `practice`, or `review` |
| `daily_goal_completed` | `completing_activity`, `streak_days` |
| `mistake_saved` | none |
| `review_queue_started` | `question_count` (max 5), `source` |
| `review_answered` | `outcome`, `attempt_number`, `next_interval_days` |
| `review_queue_completed` | `question_count`, `reviewed_count`, `first_try_correct` |
| `review_item_removed` | none |
| `video_lesson_requested` | none |
| `video_lesson_ready` | none |
| `video_lesson_completed` | none |
| `video_checkpoint_answered` | `outcome`, `checkpoint` |

Never add problem text, options/answers, OCR/image data, email/profile values, Firebase IDs, chat IDs, or question IDs. `learning_return` fires at most once per local date/session when an earlier local activity date exists. The practical funnel and scorecards live in [[growth-strategy]].

Mobile Firebase Analytics collection is disabled in both native hosts until the learner opts into “Share anonymous usage.” The adapter uses only the same low-cardinality learning/review/video outcomes, sets no analytics user ID, and never sends problem content, photos, answers, notebook IDs, email, or Firebase UID. Notifications likewise contain only generic ready copy plus an opaque validated job ID needed for the authenticated deep link.
